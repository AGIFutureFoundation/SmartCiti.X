# cloudflare/ — deploying SmartCiti.X to Cloudflare (not deployed)

**Nothing here is deployed and payments are not live.** This environment cannot reach
`api.cloudflare.com` or `api.stripe.com`, and no Cloudflare or Stripe credentials exist. This
pack is configuration and tests only; an operator with the accounts runs the steps below.

## Shape

| Piece | File | What it does |
|---|---|---|
| Pages project `smartcitix` | `wrangler.toml` | serves `_site/` (the same bundle `.github/assemble_site.sh` builds for GitHub Pages) |
| Headers | `_headers` | generated from `security/headers.json`, the canonical policy: its `site` headers on `/*` (including the baseline CSP `frame-ancestors 'none'; base-uri 'self'; object-src 'none'; form-action 'self'`), its `api` headers (deny-all CSP, `no-store`) on `/api/*`. `security/test.mjs` holds `vercel.json` to the same file |
| Redirects | `_redirects` | `/plans` to the Plans page; nothing under `/api/` |
| Routing | `_routes.json` | Functions run for `/api/*` only; everything else is a static file |
| Pages Function | `functions/api/[[path]].js` | forwards `/api/*` unchanged to the Worker via the `PAYMENTS` service binding (503 without it) |
| Worker `smartcitix-payments` | `worker/wrangler.toml` → `payments/worker.mjs` | `POST /api/checkout`, `POST /api/stripe-webhook` |

All of these except this README are generated by `python3 cloudflare/build.py`; `node cloudflare/test.mjs` checks them.

## How an operator deploys

1. In Stripe (test mode first): create one Product + Price per plan in `payments/registry/catalog.json`.
   Prices, currency, tax, trials and discounts are **set by the operator in Stripe**; this repo holds none.
2. Build and stage:
   ```sh
   python3 payments/build.py && node payments/test.mjs
   python3 cloudflare/build.py && node cloudflare/test.mjs
   bash .github/assemble_site.sh
   python3 cloudflare/build.py --stage      # copies _headers, _redirects, _routes.json into _site/
   ```
3. The Worker (from `cloudflare/worker/`):
   ```sh
   wrangler login
   wrangler kv namespace create PAYMENTS_KV     # add the printed id = ... to YOUR copy of worker/wrangler.toml; never commit it
   wrangler secret put STRIPE_SECRET_KEY        # sk_test_... first; a restricted key (rk_) with Checkout Sessions write is better
   wrangler secret put STRIPE_WEBHOOK_SECRET    # whsec_... from the webhook endpoint in step 5
   wrangler secret put SITE_ORIGIN              # e.g. https://your-domain - the only origin /api/checkout accepts
   wrangler secret put STRIPE_PRICE_INDIVIDUAL_LEARNER   # price_... (and _UNION_HALL, _SCHOOL_DISTRICT)
   wrangler secret put STRIPE_MODE_INDIVIDUAL_LEARNER    # payment | subscription (and _UNION_HALL, _SCHOOL_DISTRICT)
   wrangler secret put RATE_LIMIT_CHECKOUT_MAX           # checkout attempts per client address per plan (bucket size)
   wrangler secret put RATE_LIMIT_CHECKOUT_WINDOW_S      # seconds for the bucket to refill completely
   wrangler secret put RATE_LIMIT_SALT                   # >= 16 random characters; keys the client-address hash
   wrangler deploy
   ```
   (Price ids and modes are not secret; `wrangler secret put` simply keeps every per-deployment value out of the repo.
   Dashboard variables work too.)
4. The site (from `cloudflare/`): `wrangler pages deploy` (reads `wrangler.toml`: output `../_site`, binding `PAYMENTS`).
5. In Stripe → Developers → Webhooks: add `https://<your-domain>/api/stripe-webhook` for `checkout.session.completed`,
   copy its signing secret into `STRIPE_WEBHOOK_SECRET` (step 3).
6. Only then change the Plans page banner: it states payments are not live until a deployment really is.

## Checkout rate limit

`/api/checkout` takes one token from a bucket per (client address, plan) before it calls Stripe. The address
(`CF-Connecting-IP`) is never stored: the KV key is `HMAC-SHA256(RATE_LIMIT_SALT, address)`, truncated. The bucket
holds `RATE_LIMIT_CHECKOUT_MAX` tokens and refills completely over `RATE_LIMIT_CHECKOUT_WINDOW_S` seconds; an empty
bucket answers 429 with `Retry-After`. None of the three has a default in code: missing or invalid means 503.

*A suggestion, not policy:* `RATE_LIMIT_CHECKOUT_MAX=5`, `RATE_LIMIT_CHECKOUT_WINDOW_S=600` is a starting point for
an operator to tune against their own traffic. KV is eventually consistent, so across Cloudflare locations the limit
is approximate (a brake on abuse, not an exact quota); a Cloudflare WAF rate-limiting rule on `/api/checkout` can sit
in front of it.

## What fails closed

Missing `STRIPE_SECRET_KEY`, `SITE_ORIGIN`, a plan's price id or mode, a rate-limit setting, `STRIPE_WEBHOOK_SECRET`, the `PAYMENTS_KV`
binding or the `PAYMENTS` service binding: the route answers 503 `not_configured` and never calls Stripe.
A request whose `Origin` is not `SITE_ORIGIN` is 403. An unknown plan is 404. A webhook with a bad or old
(> 300 s) signature is 400 and nothing is stored.

## Open

- **A site-wide script/style CSP.** The pages carry inline scripts; a `script-src` needs per-page hashes (or nonces)
  computed at build time before it can be switched on. Until then `security/headers.json`'s baseline is the CSP
  (its `open` list names this and the rest).
- **A Stripe customer portal route.** Deliberately not built: `billing_portal/sessions` needs a Stripe customer
  bound to an authenticated person. With no server-side accounts, the only handle would be a Checkout Session id
  from a success URL, and anyone holding a leaked URL could then cancel someone else's subscription.
- **Entitlements.** A completed Checkout Session is recorded (`session:<id>` → plan, status, mode, livemode, time).
  Nothing yet reads it: there is no server-side account to attach it to (see `auth/`).
